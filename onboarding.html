SMS & messaging preferences

How every outbound text sounds, and when it's allowed to leave.

Send windows
These are enforced, not just recorded. Every machine calls sr_can_send() before it sends; outside the window it gets back defer plus the exact timestamp the message becomes sendable. Windows are evaluated in the tenant's own timezone, set on the Business step.
Compliance & wording
CASL: reactivation outreach is limited to existing business relationships. Opt-out language is not optional. ARRET and ARRÊT are honoured as STOP whatever the tenant's default language — the keyword handler is bilingual always, because the customer does not know which language you configured.
Review engine
Below-threshold ratings never receive the public link. They route to the owner.

Send rules & suppression

The things that stop a message going out. All four are checked by one gate that every machine calls — nothing sends without passing it.

How the gate decides. In order: is the tenant paused → is this machine allowed to send → is this number suppressed → is today a blackout → are we inside the send window → has this contact already had its daily limit. First failure wins and the reason is logged. A defer comes back with the timestamp the message becomes sendable, so nothing is silently dropped.
Blackout dates & shutdowns
Business hours are weekly and cannot express "closed the last two weeks of July" or "Christmas Day". Without these, texts fire on Christmas morning and right through their summer shutdown. Repeats annually is for fixed-date holidays; leave it off for a one-off shutdown so it doesn't come back next year.
Suppression — the do-not-contact list

Tenant-level and permanent. Every machine checks it; a STOP to any machine silences all of them.

STOP, ARRET, ARRÊT, UNSUBSCRIBE, END, QUIT and CANCEL are always honoured and cannot be removed — the keywords above are additions, not a replacement. A suppressed number survives offboarding and data deletion: you delete who they were, you keep the fact that they must not be contacted, otherwise a purge quietly re-enables texting them.
Volume limits
The tenant-per-hour cap is the blast-radius limit: if a machine misfires at 3am, this is what stops it texting the whole customer list before you wake up.

What the system does

Every trade client has different prices, phone numbers, review links and preferences about how their texts sound. Without this, plugging in a client meant hand-writing database commands each time. Now: fill the form once, submit, and every automation behaves the way that client wants. Same machines for everyone, different settings per client. That is what makes it a product rather than a custom build.

The four parts

This form Collects everything. Validates. Previews the exact JSON before sending. Full write or patch a single section.
Onboarding workflow Auth gate → validation + warnings → calls the database → reads the record back to prove the write landed → responds. Runs once per client.
Send Gate workflow The runtime half. Every machine calls it before every outbound message; it answers allow / defer / block and it fails closed. Runs on every message.
Supabase sr_tenant_profile (the business) · machine_configs (one row per machine per client) · sr_employees · sr_suppression · sr_blackout_dates · sr_send_log. Machines read settings through sr_tenant_config(tenant_id, machine_key) and ask permission through sr_can_send(...).

The checks that earn their keep

  • Missing requirement — Review Engine on with no Google review link is a blocking error. That exact bug shipped once already and looked live while sending nothing.
  • Overlap — client keeps their existing review tool and Build 3 runs autonomously → their customer gets texted twice by two systems.
  • Gap — a tool marked for cancellation while its replacement only observes → nothing covers that job once they cancel.
  • Credential owner missing — the classic install-morning stall, caught at onboarding.

How the form grows

The form is never hand-edited. Everything on the Machines step is generated.

There is one MACHINES registry at the top of the script in this file. Add one object and the form produces the card, suite grouping, status badge, settings block, required-field validation and stack-overlap check by itself.

{
  key:"build7_quote_ai",   // machine_key. NEVER rename once live.
  name:"Build 7 — AI Quoting Engine",
  suite:"Sales",           // Communication|Sales|Operations|Financial|Quality|Advanced
  status:"building",       // live | building | blocked
  defaultOn:false,
  defaultMode:"observe",   // anything unproven starts here
  competes:null,           // stack category it duplicates — ONE machine per
                           // category. "quoting" is already taken by
                           // build5_estimate_ladder, so add a new STACK entry
                           // if this needs its own overlap check.
  requires:["owner_phone"],// profile fields it cannot run without
  config:[
    {id:"max_photos", label:"Max photos per quote", type:"number", def:12},
    {id:"include_tax", label:"Show tax on the quote", type:"bool", def:true}
  ]
}

Field types: text · number · bool · select (needs opts:[[value,label]]) · textarea. Optional hint renders as grey helper text.

Machine settings need no migration — they live in machine_configs.config as jsonb. You only touch SQL when a machine needs something at the tenant level: a new number, a credential, a business-wide preference.

Three rules that will cost you an afternoon if broken

  1. Never rename a key that is already live. Tenant rows reference it; renaming orphans them. Change name freely, key never.
  2. Retire with status:"blocked", never by deleting. Deleting an entry makes existing machine_configs rows unreadable.
  3. One machine per competes category. If two claim the same one, only the first is overlap-checked and the second skips it silently. The page audits this on load and shows a red banner if you break it — add a new STACK category instead.

Versioning

Bump both, in the same commit: SCHEMA_VERSION in this file and sr_current_schema_version() in the SQL. That pair is how v_tenant_drift finds clients onboarded before a machine existed.

select * from v_tenant_drift where versions_behind > 0;
select * from sr_tenants_missing('build7_quote_ai');

Re-run those tenants through the form with their tenant_id filled in. The upsert merges config rather than replacing it, so settings written by an older form version survive.

Schema v4 — what this version added

Read this before the backlog, so you know what is genuinely built and what is only scaffolded.

Be precise about the difference. This version builds the capability: tables, RPCs, form fields, and a reusable gate sub-workflow. It does not rewire the six existing machines to call any of it. Until you do the rewiring below, a client's send window is still enforced by nothing. Saying otherwise on a sales call is the same mistake as the review-link bug — it looks live and sends nothing.
Suppression sr_suppression + sr_suppress / sr_unsuppress / sr_is_suppressed, and a bilingual sr_handle_inbound_keyword. Tenant-level, survives purge by design.
The gate sr_can_send() — master switch, machine mode, suppression, blackouts, send window in tenant timezone, three rate caps. Returns allow / defer / block with a reason, and a timestamp for defers.
Kill switch ops_status + sr_set_tenant_status(). One statement pauses every machine for one client.
Blackouts sr_blackout_dates, with correct handling of ranges that wrap the new year — the case that silently breaks a recurring Christmas shutdown.
People sr_employees, upserted on phone-or-name, leavers marked inactive rather than deleted so payroll and job history keep their references.
Credentials Account and subaccount SIDs and the name of the n8n credential. No secret is ever collected or stored.
Patch mode Change one field without a full-row overwrite. Every column is guarded by case when w_<section> … else <column> end.
Language Tenant default, secondary, and a fallback strategy; FR opt-out wording and FR phrases; per-employee language.
Billing Suites, plan, fees, term, billing day, invoice details, agreement date.
Client summary Printable confirmation from the form, and sr_client_summary() for the version generated from what was actually saved.
Offboarding sr_offboard_tenant() — pause, export, purge, complete. Purge needs an explicit confirmation string, retains the suppression list, and disables every machine. Offboarded is a one-way door: the form refuses a full write or any patch carrying personal data against a purged tenant, because that write would restore the very information the purge deleted. Reopening is a deliberate sr_set_tenant_status(...,'active').
Releasing or porting the Twilio number is still manual, in the Twilio console. Nothing in the database can do it, and forgetting it means paying monthly for a number that texts nobody.

Rewiring — the work this unblocked

The gate exists. Nothing calls it yet. This is the list that changes that, in the order that removes the most risk first.

1. Import and publish the gate

  1. Run the updated SQL. Idempotent — safe on top of the existing schema.
  2. Import 03_n8n_send_gate.json, publish it (the publish model needs it published before anything can reference it as a sub-workflow), activate.
  3. Smoke-test it standalone: call it with a known number and machine_key: "build3_review", then suppress that number with select sr_suppress(...) and call again. You want allow then block/suppressed. If it does not flip, stop and fix it before wiring anything to it.

2. Put the gate in front of every Twilio node

The pattern is the same in all six machines, and it is two nodes:

[whatever decided to send]
        │
        ├─► Execute Workflow: "SYSTEM — Send Gate"
        │     op: "check", tenant_id, phone, channel: "sms", machine_key
        │
        ├─ output 0 ALLOW ─► Twilio send ─► Execute Workflow: Send Gate
        │                                     op: "log", decision: "allow"
        ├─ output 1 DEFER ─► Wait until {{ $json.next_send_at }} ─► loop back to the gate
        │                    (and log decision: "defer")
        └─ output 2 BLOCK ─► log decision: "block" + reason, then STOP
Wire all three outputs. A defer branch that goes nowhere is a dropped message that looks like a delivered one, which is worse than the bug you started with. Re-checking the gate after the wait is not paranoia: the number may have replied STOP while the message was sitting in the queue.

3. Per-machine checklist

SMS Router Replace its private STOP handling with sr_handle_inbound_keyword on every inbound message, before the review-match branch. Its own stop_keywords config becomes additions, not the whole list. Do this one first — it is what makes STOP tenant-wide instead of router-local.
Build 3 — Review Gate all five Twilio sends. Replace the fixed 2-hour Wait with review.delay_hours from sr_tenant_config. Already reads the profile, so this is the smallest change and the best first proof.
Build 1 — Missed-Call Two jobs, and they are separate: (a) move the Google Sheets writes to Supabase; (b) gate the rescue text. Do (b) first — it is ten minutes and closes the "Build 1 texts someone who opted out of Build 3" hole. Then do (a) properly.
Build 2 — Lead Triage Gate the auto-acknowledge. Owner alerts go to the owner's own phone, not a customer — those do not go through the gate, and should not.
Build 5 — Estimate Ladder Gate every nudge. The ladder is the machine most likely to text someone at a bad time, because its sends are scheduled days ahead of the decision to send them.
DM Rescue Blocked on Meta review. Build it gated from the start rather than retrofitting.

4. Then, and only then

  1. Re-onboard the demo tenant through the form only. If you touch the SQL editor, the test failed.
  2. Prove suppression across machines: reply STOP to a Build 3 message, then trigger Build 1's rescue to the same number. It must not send. This is the single test that proves the whole layer.
  3. Prove the window: set the send window to a closed period and confirm you get defer with a sane next_send_at, not a send and not a silent drop.
  4. Prove the kill switch: sr_set_tenant_status(...,'paused'), then trigger anything.
  5. Generate the client summary and read it as if you were the client.
  6. Only now, purge the test data — one operation, never piecemeal.

Security posture

  • Webhook is protected by a shared secret (ONBOARD_SECRET), timing-safe compare, fails closed if unset.
  • The secret lives in the browser, so it protects the webhook, not the page. It is now also remembered in localStorage on whatever machine you type it into, until you press Forget. Never type it on a client's computer.
  • This file is published publicly (see the deploy notes). That is a deliberate choice, and these are its consequences — worth re-reading before each change:
    • The Handoff tab exposes the full database schema, both n8n workflows including the auth-gate logic, the backlog, and this security section. Anyone with the URL can read all of it.
    • The only thing standing between a stranger and your production database is ONBOARD_SECRET. Rotate it if it is ever pasted anywhere shared — a chat, a screenshot, a shoulder-surfed screen.
    • Never commit a real secret, a real Twilio SID, or a real tenant's data into the repo. The form ships empty; keep it that way.
    • If this stops feeling comfortable, the fix is one commit: delete the docsView div and the three text/plain source blocks. The form works unchanged without them.
  • sr_tenant_config and sr_tenant_by_number are SECURITY DEFINER and granted to service_role only — they bypass RLS and expose owner contact details and pricing.
  • sr_tenant_by_number returns a fallback tenant with matched=false for unknown numbers. Every caller must branch on matched or a stranger's call is serviced under fallback config.
  • No secrets in the profile. The form collects credential references — account SIDs and the name of an n8n credential — never a token. Both the form and the n8n validator reject a payload whose credentials object contains a key matching token / secret / password / auth. n8n holds the actual secret; the database holds the pointer.
  • Every function added in v4 is SECURITY DEFINER and granted to service_role only: sr_can_send, sr_suppress, sr_unsuppress, sr_is_suppressed, sr_handle_inbound_keyword, sr_log_send, sr_set_tenant_status, sr_client_summary, sr_offboard_tenant. Granting any of them to anon would let anyone with the public key suppress a competitor's customers or pause a tenant.
  • sr_offboard_tenant(..., 'purge') is irreversible and requires p_confirm = 'PURGE <business name>'. That friction is deliberate — it cannot fire from a mistyped parameter or a replayed audit payload.
  • sr_send_log stores a SHA-256 of the message body, not the body. Enough to spot duplicates; not a copy of your clients' customer conversations sitting in a table.

Runtime contract — what the machines call

  
The onboarding webhook runs once per client. These run on every message.

  

    
sr_can_send(
 tenant_id, phone,
 channel, machine_key)		
        Before every send, without exception. Returns
          {allowed, decision, reason, next_send_at, …} where decision is
          allow · defer · block. Checks, in order: master
          switch, machine enabled and mode, suppression, blackout dates, send window in the tenant's
          timezone, rate caps.

    
sr_log_send(…)
        After every send attempt — including blocked and deferred ones. It is both the rate-limit
          counter and the answer to "why didn't my customer get the text".

    
sr_handle_inbound_keyword(
 tenant_id, phone, body)		
        On every inbound message, before anything else looks at it. Honours STOP, ARRET, ARRÊT,
          UNSUBSCRIBE, END, QUIT, CANCEL plus any tenant additions, and START/OUI to opt back in.
          Returns {action: suppressed|released|none}.

    
sr_tenant_config(
 tenant_id, machine_key)		
        Everything else the machine needs: templates, tone, review settings, roster, credentials
          reference, language, billing status.

    
sr_set_tenant_status(…)
        The kill switch. One statement, every machine, instantly.
